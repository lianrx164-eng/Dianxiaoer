**关键原话**:「我要用 Superpowers 模式把客服系统升级成生产级架构:Workflow 确定性编排做骨架,主力 Agent 作为骨架里的核心节点。」技术栈定死 LangGraph + State + checkpointer;「转人工、建工单是两件事,分开做,都交用户在前端自选、不后端自动执行」。

**产出**:
- spec:`docs/superpowers/specs/2026-11-14-ch05-workflow-agent-design.md`(以用户桌面 Spec 为基础,按仓库现状修订)
- plan:`docs/superpowers/plans/2026-11-14-ch05-workflow-agent.md`
- ledger:`.superpowers/sdd/2026-11-14-ch05-workflow-agent/progress.md`

**纠偏(与桌面文档的差异)**:
- 桌面 Plan 里 `docker compose up -d` / `make milvus-up` / `.venv/bin/python` 与仓库不符(ch04 已定 Milvus Lite,Windows 无 Docker);全部改成 `uv run`。
- 桌面 Plan 的 `merge_dict` trace reducer 会跨轮残留上一轮 `forced_rag` 键,改成普通 dict + 每轮输入显式重置。
- 桌面 Plan 的 `should_continue` 封顶直接 `stop → log`,会把带未执行 tool_calls 的历史留给下一轮(上游 400),且答复可能为空;改成三值 `cap → cap_reply` 补合成 ToolMessage + 兜底话术。
- 桌面 Plan 的 log 节点只写 MySQL,不回填 checkpointer messages,导致确定性出口(闲聊/投诉/兜底)在下一轮历史里消失;改为确定性答复同时回填 AIMessage。
- 桌面 Plan Task 4 用裸 `with_structured_output`,与 ch04 统一入口不一致(DeepSeek 思考模式会 400);改用 `structured_model`。

**翻车与返工**:暂无。执行前确认 LangGraph 文档:`AsyncSqliteSaver.from_conn_string` 为 async context manager;`astream(stream_mode=[...])` 产出 `(mode, payload)`,`messages` 的 payload 是 `(message, metadata)`。

## 阶段 1:LangGraph 红线冒烟

**原话**:「涉及具体库、框架、API 的用法,一律先用 Context7 MCP 查最新官方文档和接口定义再动手,别凭记忆写」。

**产出**:`scripts/smoke_langgraph.py`。实跑确认(langgraph 1.2.21):
- `AsyncSqliteSaver.from_conn_string(":memory:")` 是 async context manager,`await cp.setup()` 可用。
- `astream(..., stream_mode=["messages","updates"])` 迭代出 `(mode, payload)`;`messages` 的 payload 是 `(msg, metadata)`,`metadata["langgraph_node"]` 可按节点过滤 token;`updates` 的 payload 是 `{node: state_delta}`。
- 控制台中文乱码只是 Windows GBK 显示,数据本身正常(PYTHONUTF8=1 规避)。

**纠偏**:无。**翻车**:`uv add` 输出没列 langgraph——它已作为 langchain 1.5 的依赖装好(1.2.21),版本满足要求。

## 阶段 2:祛魅——裸 Agent 循环

**原话**:「先不用框架,手写一遍最裸的 Agent 循环(调 LLM,有工具调用就执行并把结果喂回去,没有就收敛出答案),看清它就是个带工具的循环,再用 LangGraph 重构」。

**产出**:`scripts/bare_agent_loop.py`。实跑:
- 「退货政策是什么」→ 第 1 步调 `query_faq`,第 2 步无工具调用收敛。
- 「订单1001的物流到哪了」→ 第 1 步只调 `query_logistics(order_id=1001)`,第 2 步收敛——**一步搞定,不是多步**。原因是当前 `query_logistics` 吃 `order_id`,与 `query_order` 无数据依赖(印证桌面 Plan D7 的必要性)。

**结论**:Agent 循环本体就是 `for + 工具清单 + 消息数组`,LangGraph 管的是把它放进一张有状态、可持久化、可分流的大图里。

**翻车与返工**:复杂问在 D7 落地前无法多步;Task 8 改完工具后重跑验证。


## 阶段 3:State 与意图分类

**原话**:「会话状态用 LangGraph 的 State 一路贯穿」「意图识别用一个简单 prompt 判成物流、订单、商品咨询、退款退货、售后、投诉、闲聊七类,输出 JSON」。

**产出**:`app/graph/state.py`(TypedDict,`messages` 挂 `add_messages`;`trace` 普通 dict + `trace_of` 合并)、`app/core/intent.py`(结构化输出,异常/越界回退「闲聊」)、`scripts/eval_intent.py`。

**验证**:单元测试 3 + 2 通过;标注评估 **14/14** 判对。

**纠偏**:桌面 Plan 的 trace 用 `merge_dict` reducer,这里改成普通 dict + 每轮输入重置(Task 11),原因见 spec D9。意图分类改用 `structured_model`(统一 function_calling + 关闭上游思考),与 ch04 一致。
