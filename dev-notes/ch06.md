# ch06 开发追记:意图识别与对话管理

> 每完成一个阶段(brainstorm 定稿、计划评审通过、每个任务完成、code review 结论、finish)就追记一段,四样:关键原话、关键产出、拒绝/纠偏、翻车与返工。

## 阶段 0:brainstorm 定稿(2026-11-14)

**关键原话**:「我要用 Superpowers 模式把客服系统里占位的分流器做成正式版,这是 Workflow 里最关键的节点。」七条需求:指代消解+Query 改写合一、Query 扩写(严格 3 条、只退款售后)、意图四件套(8 类含「其他」+ confidence)、退款/售后确定性子流程、槽位处理(缺单弹选择器、退款原因固定下拉)、前端订单卡片+退款表单、意图模型先求准+降级路只落配置种子。

**产出**:
- spec:`docs/superpowers/specs/2026-11-14-ch06-intent-recognition-design.md`
- 分支:`ch06-intent-recognition`

**纠偏(与桌面 Spec/Plan 的差异,已写进 spec §2)**:
- 桌面文档假设基线节点名 `resolve_reference / retrieve_knowledge / main_agent`,本仓 ch05 实际是 `coref / forced_rag / agent_llm`。保留本仓名字,只把 `coref` 做实;新增 `fetch_order / retrieve_policy / script_reply`。行为与验收不变。
- 桌面 Plan 的 `docker compose` / `make milvus-up` / `.venv/bin/python` 在本仓不存在(Windows + Milvus Lite + `uv run`),命令全部改写。
- 桌面 Plan 用裸 `with_structured_output`;本仓统一 `structured_model`(DeepSeek 思考模式会 400),意图/扩写都走统一入口。
- 桌面 Plan 的闲聊文案「我暂时还不会回答这个」对「你好呀」不合适;沿用 ch05 已有问候语(已含「引回产品」),只新增「其他」文案。
- 桌面 Plan 未覆盖「暂停中用户又发新消息」。实测 langgraph 1.2.21:新输入会被接受、再次触发同一中断、新消息不处理。定为 D9:runtime 检测未决中断时重吐 `interrupt` 事件,不启动新一轮、不落库。

**本仓实测(langgraph 1.2.21,替代尚未落盘的 smoke)**:
- `ainvoke` 返回 `"__interrupt__": [Interrupt(value=...)]`,`out["__interrupt__"][0].value` 可取。
- `astream(stream_mode=["messages","updates"])` 的中断出现在 `updates` chunk:`{"__interrupt__": (Interrupt(...),)}`。
- `aget_state(config).interrupts` 是 tuple;`.next` 指向被中断节点。
- `Command(resume=v)` 从被中断节点从头重跑,`interrupt()` 返回 `v`。

**翻车与返工**:暂无。Context7 复核的官方语义与实测一致(resume 值成为 `interrupt()` 返回值、节点重启、checkpointer 存位)。

## 阶段 2:Task 1 中断 surface 冒烟

**关键原话**:「`interrupt`/`Command(resume)` 在已装 langgraph 上、经 `astream(stream_mode=["messages","updates"])` 时中断的确切 surface 形状,动手前用 `scripts/smoke_interrupt.py` 实跑钉死」。

**产出**:`scripts/smoke_interrupt.py` + `make smoke-interrupt`。实跑(langgraph 1.2.21):
- A `ainvoke` 返回 `"__interrupt__": [Interrupt(value=...)]`,取 `[0].value`;
- B `Command(resume="1001")` 续跑,`picked=1001`;
- C `astream` 中断出现在 `updates` chunk 的 `"__interrupt__"` 键;
- C' `aget_state().next=('ask_order',)`、`.interrupts` 为 tuple;
- C'' 流式 resume 从 `ask_order` 重跑,再走 `confirm`;
- D 暂停中传新输入被接受,但再次触发同一中断,新消息不处理。

**纠偏**:D 的行为写进 spec D9——runtime 检测未决中断时重吐 `interrupt`,不启动新一轮。

**翻车与返工**:无。

## 阶段 5:Task 4 意图四件套

**关键原话**:「意图识别用 LLM prompt 路线,不训分类模型,prompt 按四件套写」「强制 JSON 输出,字段就 intent 和 confidence 两个」「留「其他」兜底类,拿不准就归它」。

**产出**:

- `app/core/llm.py`:`get_chat_model(model=...)` 覆盖;意图默认 `settings.intent_model`(空回落 chat_model),保留关闭思考。

## 阶段 6:Task 5 指代消解 + 改写

**关键原话**:「用 LLM 结合对话历史,把「它能退吗」这种带指代的话补全成一句不依赖上下文也能看懂的完整问题;问题本身已完整、指代已明确的,原样透传,不强行改写」。

**产出**:`app/core/coref.py`(`resolve(query, history)`);`COREF_REWRITE_*` prompt(指代补实体、指代订单带单号、通用规则问题透传);`nodes.coref` 写 `resolved_query` + trace `coref`;`forced_rag` 改用 `resolved_query` 检索;`scripts/eval_coref.py`。

**验证**:
- 单测:`uv run pytest tests/graph/test_ch06_nodes.py tests/graph/test_forced_rag.py -q` → 10 passed(先 3 failed)。
- 评估:`make eval-coref` → **4/4**:「这个能退吗」→「蓝牙耳机能退吗」;「它到哪了」→「订单1001的猫粮物流到哪了」;两条完整问原样透传。

**纠偏**:知识路 `forced_rag` 也改用 `resolved_query`(spec 只点名意图与退款检索,但知识路拿半截话检索同样会漏,属于同一条链路的必要修正)。

**翻车与返工**:无。

## 阶段 7:Task 6 Query 扩写

**关键原话**:「把一句问题泛化成多条侧重点不同的检索查询(强制 JSON 输出,字段就 queries 一个数组),几条一起检索再去重合并;只对退款退货、售后这类高频、容错低的核心场景做」。

**产出**:`EXPAND_QUERIES_*` prompt;`query_understanding.expand_queries`(结构化输出、严格前 3 条、异常回落 `[query]`);`scripts/eval_expand.py`。

**验证**:`make eval-expand` → **3/3**,三例各出 3 条且侧重点不同、保留关键实体。

**翻车与返工**:首跑 **0/3**,全部落回落分支。排查发现 `ChatPromptTemplate` 把示例里的 `{"queries": [...]}` 当成模板变量,抛 `KeyError: missing variables {'"queries"'}`。把大括号转义成 `{{"queries": [...]}}` 后通过。这类「prompt 里写 JSON 示例」的坑后续 prompt 都要检查。

**纠偏**:无。

## 阶段 9:Task 8 retrieve_policy

**纠偏**:`search_knowledge` 参数按仓库实际用 `bm25_query`,不是桌面 Plan 的 `bm25_text`。

**翻车与返工**:无。
