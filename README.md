# 店小二 Dianxiaoer · 电商售后智能客服

把确定性写进架构里的售后对话系统:业务铁律用代码定死,模型只负责需要推理的部分,判不准就转人工。

## 为什么做这个

售后客服的失败代价不对称。模型答错一句「能退」,用户就会拿着截图来要退款,后面是真实的纠纷和赔付。这类场景要的不是更聪明的回答,而是**回答范围被工程手段限定住**:

- 退款能不能办,由售后政策和订单状态决定,不由模型决定
- 知识问答必须给出处,给不出就明说不知道
- 模型置信度低于校准过的阈值时转人工,不硬答

这套约束拆成 10 个可验收的迭代落地,每一轮都有评估集和通过线,数字在下面的「质量与评测」里。

## 能力

| 能力 | 实现方式 |
|---|---|
| 意图分流 | 8 类业务意图 + 「其他」,分流到确定性流程、知识检索、Agent 三条路 |
| 知识问答 | BM25 + 向量混合召回 → 重排 → 取 Top-K;证据不足拒答 |
| 业务工具 | 订单、物流、保修、退货状态,后端以 MCP Server 独立进程提供 |
| 退款办理 | LangGraph interrupt 暂停 → 用户点选订单并确认 → `Command(resume)` 续跑 |
| 建工单 | 写操作需确认令牌,模型绕不过 |
| 兜底转人工 | 证据置信度闸,阈值由评估集校准;低置信度问题落池 |
| 低置信度飞轮 | 落池 → 标准化 + 全表查重 + occurrence 累加 → 人工审核 → 写回知识库 |
| 主题归类 | 17 类多标签分类器,看问题集中在哪块知识,指导补什么 |

## 架构

```
客户端
  │  POST /api/chat(SSE 流)
  ▼
接入层    FastAPI 路由 + SSE 帧协议(tool / delta / done / error)
  ▼
编排层    LangGraph:意图路由 → 三条执行路
          ├─ 确定性 Workflow   政策判定、订单查询、退款流程(条件写死在代码)
          ├─ 知识检索          hybrid 召回 → rerank → 证据组装
          └─ Agent ReAct       开放问题,工具自选,步数封顶
  ▼
治理层    置信度闸 · 权限门 · 工具审计 · 中断确认
  ▼
能力层    工具注册表 · MCP Client · 知识库双写 · 主题分类器(旁路)
  ▼
数据层    MySQL(业务) · Milvus(向量) · SQLite(checkpoint)
  ▼
可观测    Phoenix(OTel span 全链路) + 按意图聚合的 token 成本账
```

**分类器走旁路。** 主题归类不进实时对话链路:低置信度问题先落池,攒够一批再离线归类写表。实时路径的延迟和可用性不依赖它。

## 关键设计决策

| 决策 | 放弃的备选 | 理由 |
|---|---|---|
| 意图分流先于 Agent | 所有问法都交给 ReAct 自选工具 | 售后问法大部分是确定的,先分类能省一次模型往返,行为也可预测 |
| 业务铁律写死在代码 | 全部写进 prompt 约束 | prompt 是建议,代码是保证;政策、金额、可退条件这类不能赌模型记性 |
| 判不准就转人工 | 让模型兜底编一个答案 | 转人工是可接受的失败,编答案是不可接受的失败 |
| 退款走 interrupt 确认 | 模型直接调 `submit_refund` | 涉及钱的动作必须有人点确认,模型没有这个权限 |
| 分类器旁路批处理 | 实时调用分类服务 | 归类结果只用于运营决策,不需要秒级一致 |
| 全参数微调 RoBERTa-wwm-ext | LoRA / 纯 prompt 分类 | 17 类多标签,单卡 8GB 放得下;全参微调便于导出 ONNX 做轻服务 |
| ONNX + tokenizers 独立进程 | 直接起 transformers | 推理进程不背 torch,依赖面小,起停快 |

## 质量与评测

| 子系统 | 指标 | 结果 |
|---|---|---|
| 自动化测试 | pytest 全量 | 410 通过 |
| 检索(ch04) | 300 题评估集,hybrid+rerank 的 recall@5 / MRR | 0.9764 / 0.9012 |
| 生成(ch04) | 库外问题拒答率 | 96.4%(56 题判定) |
| 置信度校准(ch09) | Youden J / 推荐阈值 | 0.8595 / 0.59 |
| 主题分类(ch10) | 17 类多标签,测试集 micro-F1 / macro-F1 | 0.9356 / 0.9255 |

**如实说明**:ch10 有两条严档红线未达标——尺码 0.783、退换货 0.895,各自的红线是 0.9。原因是这两类在语料里边界样本不足,错例集中在「尺码不合适」与「质量问题想退」的交叉地带。处理方式是补边界样本后重训,不是调低红线;错例明细在 `data/ch10/reports/eval_report.md`。

## 运行

前提:Python 3.12、MySQL 8.0、uv。

```bash
cp .env.example .env        # 填上游 key 与数据库连接
uv sync
uv run python scripts/seed_db.py
bash scripts/dev.sh         # :8000
```

服务拓扑:

| 服务 | 端口 | 说明 |
|---|---|---|
| 应用 | 8000 / 8002 | FastAPI,SSE 主入口 |
| 主题分类器 | 8110 | ONNX 推理,独立进程,旁路 |
| MCP 物流 / 售后 | 8101 / 8102 | mock 后端 |
| Phoenix | 6006 | 链路追踪 |

常用命令:

```bash
make dev                 # 起应用
make eval-rag            # 检索 + 生成评估
make phoenix-up          # 可观测
make ch10-eval           # 分类器评测
```

后台各页(`/admin`、`/kb`、`/review`、`/observability`、`/topics`、`/acceptance`)共用一套导航;`/acceptance` 里九个验收闸各自带重跑按钮,某个依赖挂掉只影响它自己那张卡。

## 已知限制

- 单机部署,后台页没有鉴权,只适合内网或演示环境
- 没有 CI,测试靠本地 `pytest`
- 分类器语料是真实池样本加模拟补量(每类约 100 条),不等于线上全量分布
- 上游模型的能力和价格随供应商变化,成本账按当前价格估算
- ch10 两条严档红线未达标,原因见上
